How to read this record

Verderer watches a small, curated set of U.S. government environmental pages and datasets. This page explains what it records, what its labels mean, how much of it is proven — and how to check that for yourself.

What it does

  1. It checks each source on a schedule — politely, obeying each site’s robots.txt and rate limits. Sources are re-checked several times a day.
  2. It records every distinct response. The exact bytes received are stored and their fingerprint is appended to a signed, append-only log. A re-check that returns the same bytes adds nothing.
  3. It compares each new version with the one before and lists what moved: a watched term, a number with a unit, a passage of text, a column of data, or whether the source is served at all.
  4. It publishes everything — this site, a machine-readable record, RSS feeds, the captures themselves, and proofs anyone can verify offline.

Changes and findings

A change is one comparison between two recorded versions of a source. Everything found in that comparison is a finding, so a change that removed two terms and lowered the count of a third has three findings and one headline.

When a list gains or loses an item, everything after it shifts position, and a position-by-position comparison reports each shifted item as an edit. Verderer cancels those out and shows the net effect — what was actually added or removed — with the original findings one click away.

If a later change puts back exactly what an earlier one altered, the two are linked as a reversal. Both stay on the record: that something was changed and then changed back is itself information.

Severity

Severity is a rule-based triage label that says how closely a change matches the patterns this project exists to catch. It is not a judgment about intent, or about how much a change matters.

High Something was taken away or a regulated value moved: a watched term vanished, a number with a unit changed, a dataset lost a column or rows, a source stopped being served.
Medium A real change that needs a human reading: text was edited, a watched term’s count shifted, something was added, a source came back.
Low Rewording that leaves the meaning close to what it was.

Source states

Not responding It used to answer and has stopped responding.
Live Answering normally. Its content is being recorded and compared.
Blocked The server refuses the collector. The refusal is recorded; the content is not being observed.
Gone The address returns "not found". The absence is recorded, and the watch continues.
Erroring The address returns an error status.
Unreachable It has never answered. There is nothing to record until it does.
Not collected The site's robots.txt asks crawlers not to fetch it, so it is not fetched.
Awaiting first check No check has completed yet.

A refusal is recorded as what this collector was told. It does not show that other visitors are refused, or what the page says to them.

Error-page churn

When a server refuses the collector, the body it sends is its error page, not the source. Some error pages change on every request — an “access denied” page that prints a new reference number, for instance. Each is a distinct response and is recorded, but comparing two error pages says nothing about the source, so these are set aside rather than reported as changes. This record holds 100 of them from before that rule was in place; they are kept, labelled, and left out of the counts and feeds.

What is proven, and what is not

Proven

That the collector received this response — these exact bytes, this status — from this address, and logged it at this time; and that the log has not been rewritten since. Recorded responses and findings are entries in a signed, append-only log.

Interpretation

Headlines, severities, change types, a source’s state, and which changes count as notable. They are derived from the proven entries by published rules, are best-effort, and can be re-derived or disputed.

The operator’s report

When a source was last checked, and that a check failed. A look that finds nothing new — or gets no answer — leaves no entry to sign, so this is the watchdog’s own account, not a proof.

Verderer does not claim:

  • that a response is what the agency “really” published, or what any other visitor was served;
  • anything about a source before its first recorded response;
  • why a change was made, or by whom;
  • that a time is exact — times are the collector’s clock, bounded from outside only where a proof carries an independent timestamp.

Verify it yourself

  1. Open any source and choose Verify the latest proof, or download its proof bundle.
  2. The verifier runs entirely in your browser. It checks that the captured bytes match the recorded fingerprint, that the record is in the signed log, and that the log is signed by Verderer’s published key. Nothing is uploaded.
  3. To check without this site at all, run the open-source verifier on the downloaded file: verderer-verify bundle proof.json.

Glossary

Recorded response
One fetch of a source: the bytes received, the status, the final address, and the time — signed into the log.
Content hash
A fingerprint of the exact bytes received. Change one byte and it changes completely.
Signed log
An append-only list of entries whose head is signed. Entries can be added, never altered or removed, without the signature chain exposing it.
Checkpoint
The signed statement of the log’s size and root at a moment in time.
Proof bundle
One file holding a recorded response, its bytes, and the proof that it is in the signed log — checkable offline.
WARC
The standard file format web archives use for a captured request and response.
